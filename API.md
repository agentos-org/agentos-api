# AgentOS HTTP API

Base URL: `http://<host>:<port>` (default port: `8888`).

## Authentication

Bearer token is required for all `/agentkit/*`, `/cronkit/*`, `/ragkit/*`,
`/authkit/*`, `/discoverykit/*`, and `/transferkit/*` routes, and for
`GET /appkit/subscribe`.

For `/cronkit/*`, the bearer token must be an AppKit-issued token from
`POST /appkit/register`. Cron task ownership is isolated by the token's
resolved app identity. Reads are shared within the same effective
`appGroupId`, while writes stay restricted to the owner `bundleId`.

For `/ragkit/*`, the bearer token must also be an AppKit-issued token from
`POST /appkit/register`. Rag base ownership is stored on the base metadata:
write operations are restricted to the owner `bundleId`, while reads and query
are shared within the same effective `appGroupId`.

For `/authkit/*`, most endpoints require an AppKit-issued bearer token. The
exception is `GET /authkit/userinfo`, which requires an AuthKit-issued
access token obtained through the authorization flow.

For `/discoverykit/*` and `/transferkit/*`, the bearer token must be an
AppKit-issued token from `POST /appkit/register`.

```
Authorization: Bearer <token>
```

## AgentKit (LiteAgent-Compatible Gateway)

AgentKit exposes LiteAgent-compatible routes and executes them via
LiteAgent SDK. Default LiteAgent endpoint is
`http://127.0.0.1:9527/api/v1` from `DefaultServiceLocator`.
All routes below require a Bearer token.
If backend/sdk operation fails, the gateway may return `502`.

### Endpoints

#### GET /agentkit/version

Response: `200 OK`

```
{"version":"<string>"}
```

#### POST /agentkit/initSession

Request body: `Capability`

Notes:
- `Capability.skills` is supported and forwarded as-is to LiteAgent SDK. Each item should be a complete Agent Skills markdown document.
- The source spec for each skill document is [agentskills.io/specification](https://agentskills.io/specification), especially the `SKILL.md` format with YAML frontmatter followed by Markdown content.
- `Capability.llmConfig.modelId` is also supported. AgentKit resolves `modelId` from the internal model registry, then expands it into a concrete LiteAgent `llmConfig`. The resolved model name is written to `llmConfig.model`; the gateway also fills fields such as `baseUrl`, `apiKey`, `provider`, `adapter`, and `contextWindowSize` when available.
- The gateway uses `callbackOpenTool.timeout` for external function-call waits. If omitted or invalid, it uses the 300-second compatibility default.

Response: `200 OK` (`Session`)

Example request:

Using direct LiteAgent-compatible fields:

```json
{
  "systemPrompt": "You are a helpful planner.",
  "llmConfig": {
    "baseUrl": "http://127.0.0.1:52010",
    "apiKey": "",
    "model": "qwen3-8b"
  }
}
```

Using `modelId` lookup:

```json
{
  "systemPrompt": "You are a helpful planner.",
  "llmConfig": {
    "modelId": "qwen3-8b"
  }
}
```

Example response:

```json
{"sessionId":"session-1"}
```

#### POST /agentkit/initSimple

Request body: `SimpleCapability`

Notes:
- `SimpleCapability.skills` is supported and forwarded as-is to LiteAgent SDK. Each item should be a complete Agent Skills markdown document.
- The source spec for each skill document is [agentskills.io/specification](https://agentskills.io/specification), especially the `SKILL.md` format with YAML frontmatter followed by Markdown content.
- `SimpleCapability.llmConfig.modelId` is also supported and follows the same resolution behavior as `/agentkit/initSession`.

Response: `200 OK` (`Session`)

#### POST /agentkit/chat

Query:

| Field | Type | Required |
| --- | --- | --- |
| `sessionId` | `string` | Yes |

Request body: `UserTask`.

`llmConfig` is optional. When supplied, it overrides the session's default LLM
configuration for this request only; it does not modify the session. For a
direct override, pass the complete LiteAgent-compatible configuration rather
than only the fields being changed. AgentKit also accepts the gateway-only
`llmConfig.modelId` field and resolves it through the internal model registry.

The request-level `llmConfig` fields are:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `llmConfig.modelId` | `string` | No | AgentKit-only model registry ID. When provided, AgentKit resolves it to a concrete model configuration and fills `baseUrl`, `model`, `apiKey`, `provider`, `adapter`, and `contextWindowSize` when available. It can be used instead of the direct `baseUrl`/`model` fields; request-level tuning fields can still be supplied. |
| `llmConfig.provider` | `string` | No | `openai` or `lite_oneapi`. |
| `llmConfig.baseUrl` | `string` | Yes | LLM provider API endpoint. |
| `llmConfig.apiKey` | `string` | Yes | LLM provider API key. |
| `llmConfig.model` | `string` | Yes | Model name for this request. |
| `llmConfig.adapter` | `string` | No | Upstream protocol/provider adapter used with `provider=lite_oneapi`. |
| `llmConfig.temperature` | `number` | No | Sampling temperature; LiteAgent default is `0`. |
| `llmConfig.maxTokens` | `number` | No | Maximum token count; LiteAgent default is `4096`. |
| `llmConfig.contextWindowSize` | `number` | No | Context window size. |
| `llmConfig.topP` | `number` | No | Top-p sampling value; LiteAgent default is `1`. |
| `llmConfig.supportsToolCall` | `boolean` | No | Whether the model supports tool calling; LiteAgent default is `true`. |
| `llmConfig.supportsReasoning` | `boolean` | No | Whether the model supports reasoning; LiteAgent default is `false`. |

Response: `200 OK`, `text/event-stream`

Events:
- `message`: `AgentMessage`
- `chunk`: `AgentMessageChunk`
- `functionCall`: `{"sessionId":"<string>","functionCall":FunctionCall}`. For a
  stream-capable function call, the gateway also includes `"stream":true`.

Example request:

```json
{
  "content": [
    {"type": "text", "message": "Summarize this repository."}
  ],
  "isChunk": true,
  "llmConfig": {
    "provider": "lite_oneapi",
    "baseUrl": "https://your-oneapi-server/v1",
    "apiKey": "sk-xxxxxxxxxx",
    "model": "qwen-plus",
    "adapter": "qwen"
  }
}
```

#### POST /agentkit/chat/simple

Query:

| Field | Type | Required |
| --- | --- | --- |
| `sessionId` | `string` | Yes |

Request body: `UserTask`.

`llmConfig` has the same request-only override semantics as `/agentkit/chat`:
it overrides the session's default for this request and does not update the
session. Pass the complete configuration for a direct override. AgentKit's
gateway-only `llmConfig.modelId` lookup is also supported.

The request-level `llmConfig` fields are the same as `/agentkit/chat`:
`modelId`, `provider`, `baseUrl`, `apiKey`, `model`, `adapter`, `temperature`,
`maxTokens`, `contextWindowSize`, `topP`, `supportsToolCall`, and
`supportsReasoning`.

Example request:

```json
{
  "content": [
    {"type": "text", "message": "Give me a random number."}
  ],
  "llmConfig": {
    "provider": "lite_oneapi",
    "baseUrl": "https://your-oneapi-server/v1",
    "apiKey": "sk-xxxxxxxxxx",
    "model": "qwen-plus",
    "adapter": "qwen"
  }
}
```

Response: `200 OK` (`AgentMessage`)

Example response:

```json
{
  "sessionId": "session-1",
  "taskId": "task-1",
  "role": "llm",
  "to": "user",
  "type": "text",
  "content": "This repository provides a unified API gateway for local AI services.",

```

#### POST /agentkit/callback

Query:

| Field | Type | Required |
| --- | --- | --- |
| `sessionId` | `string` | Yes |

Request body: `ToolReturn`

Response: `200 OK`

```json
{"status":"ok"}
```

Notes:
- If there is a pending external `functionCall` for the same `sessionId` + `toolReturn.id`, this endpoint completes that pending call.
- A late callback for a gateway-proxied call that already expired or completed returns `200 OK` with `{"status":"ignored","reason":"callback_expired"}` or `callback_completed`, and is not forwarded downstream.
- Otherwise, the request is forwarded to LiteAgent `/callback` (legacy behavior).

Example request:

```json
{
  "id": "call-1",
  "result": {
    "ok": true,
    "content": "Tool execution finished."
  }
}
```

#### POST /agentkit/streamCallback

Query:

| Field | Type | Required |
| --- | --- | --- |
| `sessionId` | `string` | Yes |

Request body: `EventToolReturn`

Response: `200 OK`

```json
{"status":"ok"}
```

Example request:

```json
{
  "event": "functionCall",
  "toolReturn": {
    "id": "call-1",
    "result": {
      "ok": true,
      "content": "Tool execution finished."
    }
  }
}
```

Notes:
- This endpoint is the stream-oriented callback companion to `/agentkit/callback`.
- It is typically used when the client keeps event context and wants to return a tool result tagged with the original stream event type.
- Late stream events for expired or completed gateway-proxied calls use the same `200 OK` ignored response and are not forwarded downstream.

### LiteAgent compatibility boundary

AgentKit exposes the LiteAgent-compatible endpoints listed above. LiteAgent's
server-only `/presetOpenSpecList` and `/session/subscribe` endpoints are not
currently proxied under `/agentkit`; configure those against LiteAgent itself
when needed.

## AppKit

### POST /appkit/register

Request body:

```
{"bundleId":"com.demo.app","appGroupId":"com.demo"}
```

Response: `200 OK`

```
{"token":"sk-...","bundleId":"com.demo.app","appGroupId":"com.demo"}
```

Example request without explicit `appGroupId`:

```json
{"bundleId":"com.demo.app"}
```

Example response:

```json
{"token":"sk-...","bundleId":"com.demo.app","appGroupId":"com.demo.app"}
```

Notes:
- `appGroupId` is optional.
- If omitted, the server uses `bundleId` as the effective group ID.

An app may also declare local OpenTool server dependencies by stable `ref`
and server `name`:

```json
{
  "bundleId": "com.demo.app",
  "opentoolServers": [
    {"ref": "websearch", "name": "opentool-server-websearch"}
  ]
}
```

Registration always selects the highest semantic version installed for the
name. Apps cannot pin a specific server version. If none of the matching
versions are semantic versions, daemon list order is retained as the fallback.

This integration requires OpenTool daemon API v2 with the
`artifactRegistryV2` and `startToolTerminalV1` capabilities (daemon 0.5.0 or
newer). Older daemon contracts are rejected before Server or Tool payloads are
read.

The gateway checks the local OpenTool daemon before returning. A ready tool
returns its callable `id`; a tool being launched and a missing local server do
not return an `id`:

```json
{
  "token": "sk-...",
  "bundleId": "com.demo.app",
  "appGroupId": "com.demo.app",
  "opentoolServers": [
    {
      "ref": "websearch",
      "server": {
        "namespace": "local",
        "repo": "local",
        "name": "opentool-server-websearch",
        "version": "1.2.0",
        "tag": "1.2.0"
      },
      "status": "running",
      "id": "tool-..."
    }
  ]
}
```

Possible registration statuses are `running`, `starting`, and `notFound`.
`id` is present only for `running`. Starting continues asynchronously; its
eventual success or failure is delivered by `GET /appkit/subscribe`.

OpenTool V2 clients should use `namespace` and `version`. AppKit also emits the
deprecated aliases `repo` and `tag` with identical values in registration and
subscription event `server` objects so already-distributed legacy SDK clients
remain compatible. The aliases are an AppKit response compatibility layer;
the daemon contract remains V2-only.

### GET /appkit/subscribe

Requires Bearer token (token from `/appkit/register`).

Response: `200 OK`, `text/event-stream`.

Event examples:

```
event: welcome
data: {"bundleId":"com.demo.app"}

```

New business notifications use the generic `appEvent` envelope. When ToolKit
finishes provisioning a local OpenTool server that returned `starting`, it
emits the ready tool ID:

```text
id: evt-...
event: appEvent
data: {"version":1,"id":"evt-...","type":"toolkit.provision.succeeded","source":"toolkit","time":"2026-07-15T10:30:00.000Z","subject":"websearch","data":{"ref":"websearch","name":"opentool-server-websearch","status":"running","server":{"namespace":"local","name":"opentool-server-websearch","version":"1.2.0"},"id":"tool-..."}}

```

If provisioning fails instead, it emits:

```text
id: evt-...
event: appEvent
data: {"version":1,"id":"evt-...","type":"toolkit.provision.failed","source":"toolkit","time":"2026-07-15T10:30:00.000Z","subject":"websearch","data":{"ref":"websearch","name":"opentool-server-websearch","status":"failed","server":{"namespace":"local","name":"opentool-server-websearch","version":"1.2.0"},"error":{"code":"startFailed","message":"..."}}}

```

After a declared tool becomes ready, AgentOS monitors both the OpenTool daemon
and the concrete tool process. If either becomes unavailable, it emits:

```text
id: evt-...
event: appEvent
data: {"version":1,"id":"evt-...","type":"toolkit.tool.unavailable","source":"toolkit","time":"2026-07-15T10:35:00.000Z","subject":"websearch","data":{"ref":"websearch","name":"opentool-server-websearch","id":"tool-...","status":"unavailable","scope":"tool","reason":"healthcheckFailed","server":{"namespace":"local","name":"opentool-server-websearch","version":"1.2.0"}}}

```

`scope` is `daemon` when the daemon stopped, errored, or could not be reached;
otherwise it is `tool`. Tool reasons include `removed`, `stopped`, and
`healthcheckFailed`. Daemon reasons include `daemonStarting`, `daemonStopped`,
`daemonError`, and `daemonUnavailable`.

When the same tool is healthy again, AgentOS emits the symmetric transition:

```text
id: evt-...
event: appEvent
data: {"version":1,"id":"evt-...","type":"toolkit.tool.available","source":"toolkit","time":"2026-07-15T10:35:05.000Z","subject":"websearch","data":{"ref":"websearch","name":"opentool-server-websearch","id":"tool-...","status":"running","scope":"tool","reason":"recovered","server":{"namespace":"local","name":"opentool-server-websearch","version":"1.2.0"}}}

```

Availability events are transition-based: repeated checks in the same state do
not emit duplicates. The `id` identifies the concrete OpenTool instance that
was returned by registration or `toolkit.provision.succeeded`.

If the app has not subscribed yet, AppKit events are queued and sent immediately
after `welcome`. Apps should treat `toolkit.provision.succeeded` as the point at
which a declaration that returned `starting` becomes callable, and stop using a
tool after `toolkit.tool.unavailable` until `toolkit.tool.available` arrives.
The `app.command.requested` type is reserved for future commands sent to apps.

If the token is missing or invalid, returns `401`.

## AuthKit

AuthKit provides OAuth-like authorization for third-party apps. It lets
external apps request user consent, exchange an authorization code for an
access token, and retrieve AgentOS user information.

All endpoints except `GET /authkit/userinfo` require an AppKit-issued bearer
token (`POST /appkit/register`). `GET /authkit/userinfo` requires an
AuthKit-issued access token obtained through the authorization flow.

### Authorization Flow

1. App calls `POST /authkit/authorize` to create an authorization request.
2. If the app was previously authorized, response is `200` with `authCode`.
   Otherwise response is `202` with `status: "pending"`.
3. For pending requests, poll `GET /authkit/authorize/<requestId>/status`
   until `status` becomes `granted` (with `authCode`), `denied`, or `timeout`.
4. Exchange the `authCode` for an access token via `POST /authkit/token`.
5. Use the access token to call `GET /authkit/userinfo`.
6. Revoke a grant with `POST /authkit/revoke`.

Pending requests expire after 3 minutes.

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `requestId` | `string` | Yes | Authorization request ID. |
| `status` | `string` | Yes | `pending`, `granted`, `denied`, or `timeout`. |
| `authCode` | `string` | No | Present when `status` is `granted`. |

#### TokenResponse

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `accessToken` | `string` | Yes | AuthKit access token (prefixed `akt-`). |
| `userId` | `string` | No | Stable per-app user ID (SHA-256 derived). |

| `userInfo.name` | `string` | Yes | User display name. |
| `userInfo.avatarUrl` | `string` | Yes | User avatar URL (may be empty). |

#### UserInfo

## ToolKit API

ToolKit is the gateway entry point for tool runtime APIs. External clients call
`/toolkit/*` on the AgentOS API Gateway; they do not need to know or call the
internal tool runtime path. Server build/import APIs are managed by the platform
and process lifecycle APIs are not exposed as public ToolKit APIs.

ToolKit requests require the Bearer token returned by `POST /appkit/register`.

For a gateway running on the default port:

```bash
TOKEN=$(curl -s http://127.0.0.1:8888/appkit/register \
  -H 'content-type: application/json' \
  -d '{"bundleId":"com.demo.app"}' | jq -r .token)
curl http://127.0.0.1:8888/toolkit/list \
  -H "authorization: Bearer $TOKEN"
```

### Authentication

All ToolKit endpoints require:

```http
Authorization: Bearer <token returned by POST /appkit/register>
```

Missing or invalid tokens return `401`.

### Endpoint Summary

| Method | Path | Description |
| --- | --- | --- |
| GET | `/toolkit/list` | List running tools, or all tools with `all=1`. |
| POST | `/toolkit/{toolId}/call` | Call a tool function. |
| POST | `/toolkit/{toolId}/streamCall` | Call a tool function with SSE results. |
| GET | `/toolkit/{toolId}/load` | Return the tool description and function schemas. |

## ModelKit (Proxy to Model Services)

ModelKit is the task-oriented gateway for direct model access. Use AgentKit
when you need agents, sessions, tools, or multi-step orchestration; use
ModelKit when you need to call a model capability directly.

ModelKit exposes stable task routes and forwards requests to the matching local
or remote model backend. Request bodies, query parameters, and most headers are
passed through to the upstream service. The gateway only adds routing,
model-resolution, metrics, and compatibility handling.

ModelKit routes do not require an AgentOS bearer token. For remote models, the
gateway resolves provider credentials from the registered model metadata or the
kernel default LLM configuration.

### Endpoint Summary

| Endpoint | Description |
| --- | --- |
| `GET /modelkit/models` | List available models in the task-oriented ModelKit schema |
| `GET /modelkit/chat/models` | List chat models in OpenAI-compatible format |
| `GET /modelkit/chat/v1/models` | Alias for `/modelkit/chat/models` |
| `ALL /modelkit/chat` | Forward to the chat default endpoint (`/chat/completions`) |
| `ALL /modelkit/chat/*` | Forward to a custom chat upstream path |
| `ALL /modelkit/embedding` | Forward to the embedding default endpoint (`/embeddings`) |
| `ALL /modelkit/embedding/*` | Forward to a custom embedding upstream path |
| `ALL /modelkit/asr` | Forward to the ASR default endpoint (`/audio/transcriptions`) |
| `ALL /modelkit/asr/*` | Forward to a custom ASR upstream path |
| `ALL /modelkit/tts` | Forward to the TTS default endpoint (`/audio/speech`) |
| `ALL /modelkit/tts/*` | Forward to a custom TTS upstream path |
| `GET /modelkit/app-models` | List all app-registered models |
| `POST /modelkit/app-models` | Register a model from a third-party app |
| `PUT /modelkit/app-models/<id>` | Update an app-registered model |
| `DELETE /modelkit/app-models/<id>` | Unregister an app-registered model |
| `POST /modelkit/app-models/<id>/toggle` | Toggle an app-registered model's disabled state |

### Common Schemas

#### ModelInfo

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `id` | `string` | Yes | Unique 12-character hash-style model ID used by the gateway for routing and lookup. |
| `name` | `string` | Yes | Upstream model name. For remote models, the gateway may rewrite request body `model` from `id` to this value before forwarding. |
| `alias` | `string` | Yes | Human-friendly model alias. |
| `description` | `string` | Yes | Model description from the service locator. |
| `task` | `string` | Yes | `chat`, `embedding`, `asr`, or `tts`. |
| `input` | `string[]` | Yes | Input modalities, such as `text`, `image`, or `audio`. |
| `output` | `string[]` | Yes | Output modalities, such as `text` or `audio`. |
| `capabilities` | `ModelCapabilities` | Yes | Capability flags. |
| `contextWindowSize` | `number` | No | Context window size when provided by the backing model metadata. |

| `isAppModel` | `boolean` | No | Present and `true` when the model was registered by a third-party app via the App Model Registration API. |

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `vision` | `boolean` | Yes | Whether the chat model accepts image input. Vision-language models use `/modelkit/chat`; there is no separate vision task route. |
| `tool_call` | `boolean` | Yes | Whether tool/function calling is supported. |
| `stream` | `boolean` | Yes | Whether streaming responses are supported. |
| `reasoning` | `boolean` | Yes | Whether reasoning output is supported by the model metadata. |

#### Common Request Fields

ModelKit forwards the upstream model service protocol. For OpenAI-compatible
backends, the following fields are commonly used:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `model` | `string` | Usually | Model identifier. Prefer the unique `id` returned by `GET /modelkit/models`; the gateway also accepts a resolvable model `name` for compatibility. For `/modelkit/chat`, if omitted, the gateway may use the kernel default LLM configuration. |
| `stream` | `boolean` | No | When true, chat responses are streamed as `text/event-stream`. The gateway also treats requests with `Accept: text/event-stream` as streaming requests. |
| `base_url` | `string` | No | Optional base URL hint for metrics. Routing still resolves through the model registry and service locator. |

### Routing Contract

ModelKit path prefixes select a task. The task root maps to a default upstream
endpoint. A sub-path is forwarded as the requested upstream path.

| Public Path | Task | Default Upstream Path | Typical Content Type | Typical Response |
| --- | --- | --- | --- | --- |
| `/modelkit/chat` | `chat` | `/chat/completions` | `application/json` | JSON chat completion or SSE stream |
| `/modelkit/embedding` | `embedding` | `/embeddings` | `application/json` | JSON embedding response |
| `/modelkit/asr` | `asr` | `/audio/transcriptions` | `multipart/form-data` | JSON or text transcription |
| `/modelkit/tts` | `tts` | `/audio/speech` | `application/json` | Audio bytes or provider response |

Examples:

| Request Path | Forwarding Behavior |
| --- | --- |
| `POST /modelkit/chat` | Uses the chat task default endpoint |
| `POST /modelkit/chat/v1/chat/completions` | Forwards to the chat backend with that explicit path |
| `GET /modelkit/tts/audio/voices` | Forwards to the TTS backend voice-list endpoint |

For chat responses, ModelKit normalizes OpenAI-compatible JSON and SSE details
where needed, including `data: ` SSE framing, `reasoning_content`, and tool-call
delta compatibility. For TTS voice-list responses, filesystem paths in voice
keys may be reduced to basenames.

| --- | --- | --- | --- |
| `model` | `string` | Yes | Stable ASR model `id` from `/modelkit/models`. |
| `file` | `file` | Yes | Audio file to transcribe. |
| `language` | `string` | No | Language hint, if supported by the upstream backend. |
| `response_format` | `string` | No | Provider-specific response format, such as `json` or `text`. |

Example request:

```bash
curl -X POST http://localhost:8888/modelkit/asr \
  -F model=whisper-local \
  -F file=@sample.wav \
  -F response_format=json
```

Example response:

```json
{
  "text": "Welcome to AgentOS."
}
```

#### ALL /modelkit/tts

Forwards a text-to-speech request to the resolved TTS backend. The root path
maps to the upstream `/audio/speech` endpoint.

Common JSON request body:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `model` | `string` | Yes | Stable TTS model `id` from `/modelkit/models`. |
| `input` | `string` | Yes | Text to synthesize. |
| `voice` | `string` | No | Voice name supported by the upstream backend. |
| `response_format` | `string` | No | Audio format, if supported by the upstream backend. |

Example request:

```bash
curl -X POST http://localhost:8888/modelkit/tts \
  -H 'Content-Type: application/json' \
  -o speech.wav \
  -d '{
    "model": "qwen-tts",
    "input": "Welcome to AgentOS.",
    "voice": "default",
    "response_format": "wav"
  }'
```

Response: audio bytes with the upstream content type, or a provider-specific
JSON response.

Voice-list example:

```bash
curl http://localhost:8888/modelkit/tts/audio/voices
```

#### GET /modelkit/chat/models

Lists available chat models in the OpenAI-compatible wire format. This endpoint
aggregates all available chat models (remote and local) into a single
`{"object": "list", "data": [...]}` payload, matching the shape that llama.cpp
and OpenAI clients expect. Only models whose resolved task is `chat` are
included.

`GET /modelkit/chat/v1/models` is an alias with the same behavior.

Response: `200 OK`

```json
{
  "object": "list",
  "data": [
    {
      "id": "qwen3-8b (Qwen 3 8B)",
      "aliases": ["Qwen 3 8B", "qwen3-8b"],
      "tags": [],
      "object": "model",
      "created": 1727654400,
      "owned_by": "openai",
      "meta": {
        "n_ctx": 8192
      }
    }
  ]
}
```

The `id` field is a display-oriented label built from the model's alias and
name (format: `alias (name)` when they differ, or just the alias/name). The
`aliases` array contains both `name` and `alias` for lookup flexibility. The
`meta.n_ctx` field carries the context window size when available.

#### App Model Registration API

Third-party applications can register their own models with ModelKit so that
they appear in the unified `/modelkit/models` listing and can be accessed
through the standard ModelKit proxy routes. App-registered models are
persisted and survive gateway restarts.

These endpoints do not require a bearer token.

##### AppModelData Schema

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `id` | `string` | Yes | Unique model identifier. |
| `name` | `string` | Yes | Model display name. |
| `alias` | `string` | No | Human-friendly model alias. |
| `description` | `string` | No | Model description. |
| `task` | `string` | No | Model task: `chat` (default), `embedding`, `asr`, or `tts`. |
| `provider` | `string` | No | Provider identifier (default: `openai_compatible`). |
| `input` | `string[]` | No | Input modalities (e.g. `["text"]`). |
| `output` | `string[]` | No | Output modalities (e.g. `["text"]`). |
| `capabilities` | `object` | No | Capability flags: `stream` (bool, default true), `tool_call` (bool, default false), `reasoning` (bool, default true). |
| `baseUrl` | `string` | No | Model endpoint base URL. |
| `apiKey` | `string` | No | API key for authenticating with the model endpoint. |
| `contextWindowSize` | `number` | No | Context window size. |
| `appBundleId` | `string` | Yes | Bundle ID of the registering app. |
| `appName` | `string` | No | Display name of the registering app. Defaults to `appBundleId`. |

When listing app models, the response replaces `apiKey` with `hasApiKey`
(boolean) to avoid exposing credentials.

##### GET /modelkit/app-models

Lists all models registered by third-party apps.

Response: `200 OK` (`AppModelData[]`)

```json
[
  {
    "id": "example-gpt4o",
    "name": "GPT-4o",
    "alias": "gpt-4o",
    "description": "OpenAI GPT-4o model",
    "task": "chat",
    "provider": "openai_compatible",
    "input": ["text"],
    "output": ["text"],
    "capabilities": {
      "stream": true,
      "tool_call": true,
      "reasoning": false
    },
    "baseUrl": "https://api.openai.com/v1",
    "hasApiKey": true,
    "contextWindowSize": 128000,
    "isDisabled": false,
    "appBundleId": "com.example.myapp",
    "appName": "My Example App"
  }
]
```

##### POST /modelkit/app-models

Registers a new model from a third-party app. The model will appear in
`GET /modelkit/models` and can be accessed through the standard proxy routes.

Request body: see AppModelData schema above. `id`, `name`, and `appBundleId`
are required.

Example request:

```bash
curl -X POST http://localhost:8888/modelkit/app-models \
  -H 'Content-Type: application/json' \
  -d '{
    "id": "example-gpt4o",
    "name": "GPT-4o",
    "alias": "gpt-4o",
    "description": "OpenAI GPT-4o model",
    "appBundleId": "com.example.myapp",
    "appName": "My Example App",
    "task": "chat",
    "provider": "openai_compatible",
    "input": ["text"],
    "output": ["text"],
    "capabilities": {
      "stream": true,
      "tool_call": true,
      "reasoning": false
    },
    "baseUrl": "https://api.openai.com/v1",
    "apiKey": "sk-...",
    "contextWindowSize": 128000
  }'
```

Response: `200 OK`

```json
{
  "success": true,
  "id": "example-gpt4o"
}
```

##### PUT /modelkit/app-models/\<id\>

Updates an existing app-registered model. Only the fields provided in the
request body are updated; omitted fields retain their current values. The
`apiKey` field is only overwritten when a non-empty value is provided.

Example request:

```bash
curl -X PUT http://localhost:8888/modelkit/app-models/example-gpt4o \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "GPT-4o Updated",
    "description": "Updated description",
    "contextWindowSize": 256000
  }'
```

Response: `200 OK`

```json
{
  "success": true
}
```

Returns `404` if the model is not found.

##### DELETE /modelkit/app-models/\<id\>

Unregisters an app-registered model.

Example request:

```bash
curl -X DELETE http://localhost:8888/modelkit/app-models/example-gpt4o
```

Response: `200 OK`

```json
{
  "success": true
}
```

Returns `404` if the model is not found.

##### POST /modelkit/app-models/\<id\>/toggle

Toggles the disabled state of an app-registered model. A disabled model
remains registered but is excluded from active model listings and proxy
routing.

Example request:

```bash
curl -X POST http://localhost:8888/modelkit/app-models/example-gpt4o/toggle \
  -H 'Content-Type: application/json' \
  -d '{}'
```

Response: `200 OK`

```json
{
  "success": true
}
```

Returns `404` if the model is not found.

### Error Responses

If no local service or remote route is available for the selected task/model,
returns `503`:

```json
{
  "error": "Model \"qwen3-8b\" unavailable",
  "service": "llm_chat"
}
```

If a backend connection error occurs, returns `502`:

```json
{
  "error": "Backend service unavailable",
  "service": "llm_chat",
  "message": "Connection refused"
}
```

If the upstream reports a context-window overflow, ModelKit normalizes common
provider-specific errors to `400`:

```json
{
  "error": {
    "message": "This model's maximum context length is 8192 tokens. However, your messages resulted in 12000 tokens. Please reduce the length of the messages.",
    "type": "context_length_exceeded",
    "code": "context_length_exceeded",
    "n_prompt_tokens": 12000,
    "n_ctx": 8192
  }
}
```
